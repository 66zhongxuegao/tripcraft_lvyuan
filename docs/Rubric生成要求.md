# Rubric 数据底座 · 生成要求（给联网大模型）

> 版本：v1.0 ｜ 日期：2026-10-07
> 用途：指导一个**能联网的大模型**按统一规格生成 61 个技能点的 Rubric（BARS 行为锚定评分标准）。
> 对应代码：生成结果需能被 `tripcraft/contracts/rubric.py` 直接导入。
> 上游依据：PRD 第 17 章（61 技能点）、第 18 章（对齐 Rubric）、第 19 章（A/B 考点）。

---

## 0. 一句话要求

**为指定的每一个技能点，产出「考核定位 + M1–M5 行为锚点 + 正例 + 反例 + 证据要求 + 关联知识点」的严格 JSON，锚点必须是可观测行为、且能被打分 Agent 逐字对照。**

---

## 1. 为什么分批：先 S2，再全量

M1 是「S2 首呼」垂直切片。要跑通 S2，只需要 S2 涉及的 Rubric。这是**为了开工**，不是"只需要这些"。

**第一批（国内切片，6 个）**：
C1.1 开场与身份确认 / C1.2 顾问式提问 / C1.3 情绪安抚 / C1.6 应对不耐烦追问 / C2.1 信息挖掘（缺失字段识别） / C2.2 预算口径识别

**同批（入境切片，3 个，可第二批）**：
C8.1 外籍客户多语种首呼 / C8.2 国别沟通风格适配 / C8.4 时差与通讯工具切换

**后续批次**（按步骤分批，避免一次生成 61 个导致质量下降）：
S3(5) → S4(7) → S5(9) → S6(10) → S7(6) → S8(5) → S9(6) → S10(9) → S11(6)

> 原则：**每批 5–10 个**，生成后立刻自检 + 入库校验，再进下一批。

## 2. 先决输入（必须一并喂给模型）

生成时必须给出以下四项，缺一不可：

### 2.1 技能点信息（来自 `contracts/skill_points.py`）
技能点 ID、名称、所属维度、考点类型（A/B）、学习资料、涉及步骤、**考核定位（步骤·考核对象）**。

### 2.2 录音提炼的硬规则（PRD 第 13 章，不可违背）
1. 同一客户可能同时派给 3 位定制师，联系慢了就丢单。
2. 派单信息经常缺失，必须电话首呼补问。
3. 系统要求 1 小时内打电话、4 小时内上传方案。
4. 必须先确认酒店、车、票、导游等资源，再给客户确定报价。
5. 资源可先付约 80% 预留，最后结全款。
6. 定制游必须买保险。
7. 方案最终做成 PPT，再转 PDF 发给客户。
8. 行前 1–2 天发出团通知书。
9. 行中客户不会找地接社，最终都找定制师，定制师是全程第一责任人。
10. 行后要拿地接结算单和自己的报价逐项核对，再付尾款。

### 2.3 学习模块清单（知识点只能从这里来，禁止编造课程）
行业认知 / 沟通服务 / 需求管理 / 目的地资源 / 国别文化 / 方案设计 / 视觉呈现 / 实操注意 / 入境中国

### 2.4 金标准示例（模型必须模仿其粒度）
C2.2 预算口径识别（见第 6 节）。

## 3. 输出格式（严格 JSON，一个技能点一个对象）

```json
{
  "skill_point_id": "C2.2",
  "name": "预算口径识别",
  "dimension": "C2",
  "checkpoint": "B",
  "steps": ["S2", "S6"],
  "target": "是否把「性价比高」当预算已明确",
  "trigger": "客户说「性价比高」",
  "anchors": {
    "M1": "全程未追问预算，直接按「性价比高」做方案/报价",
    "M2": "只问「预算多少」，客户答「性价比高」就停止",
    "M3": "追问「人均还是总价」，但没确认区间、是否含大交通",
    "M4": "问到人均/总价+区间，但未二次复述确认",
    "M5": "追问并量化确认（人均/总价+区间+是否含大交通），复述得到确认"
  },
  "positive": "「您的预算是人均还是整团总价？大概区间？含不含机票高铁？」并复述确认",
  "negative": "客户说「性价比高」就当成预算已明确，报价被否定",
  "evidence_required": "引用 S2 通话转写中关于预算的问答原文",
  "knowledge": "需求管理·期望管理——「性价比高 ≠ 预算明确」；KANO（预算属硬约束）",
  "sources": ["（依据：PRD 第 13 章硬规则 4/6；需求管理模块）"]
}
```

字段规则：
- `trigger`：**B 型必填**；A 型填 `null`。
- `anchors`：必须**恰好**包含 M1–M5 五个键。
- `sources`：联网查到的依据；纯理论无外部事实时可写 `["依据：PRD 第 X 章"]`；**不确定的写 `["待核实"]`**。

---

## 4. 质量规则（硬性，违反即作废）

1. **锚点必须是可观测行为**：能从通话转写、消息记录或交付物里"看到/读到"学员做了什么、说了什么。
   - 反例（作废）：「表现较好」「沟通能力强」「理解到位」——这是评价，不是行为。
   - 正例：「只问『预算多少』，客户答『性价比高』就停止」。
2. **M1–M5 必须单调递进在同一根轴上**：只能沿同一个能力维度从差到好，不能 M3 考 A 能力、M4 考 B 能力。
3. **相邻档必须可区分**：M3 和 M4 不能听起来一样；每一级都要有"多做了哪一步/少做了哪一步"。
4. **正例是可直接照说的台词/动作**：给模板句，不要只写"应主动确认"。
5. **反例是真实常见错误**：来自行业常见翻车点，不是生造的极端案例。
6. **证据要求必须具体**：写清"引用哪一步的什么记录（原话/字段）"，不能只写"要有证据"。
7. **知识点只能来自 9 个学习模块**；写清"模块·知识点"。
8. **B 型必须给触发条件**：说明"什么刺激会让这个技能显现"。
9. **不得与硬规则冲突**（如不得出现"可以先报死价"这类表述）。

---

## 5. 联网与反幻觉要求

1. 涉及**具体目的地、签证/免签政策、宗教饮食禁忌、汇率/支付**等事实时，**必须联网核对并给出处**。
2. 查不到权威来源的，写 `["待核实"]`，**不得编造**。
3. 不得虚构"某条规定""某本书第几章"。
4. 不得把"通用常识"包装成"法规要求"。
5. 输出前**逐条自检**（见第 7 节），不合规的自行重写。

---

## 6. 金标准示例（C2.2，模型必须模仿此粒度）

见第 3 节 JSON。若干要点：
- M1 到 M5 是一条线：**没问 → 问了没量化 → 量化了没全覆盖 → 全覆盖了没复述 → 全覆盖+复述确认**。
- 正例是可复述的台词。
- 证据要求落到"哪一步的哪段原文"。
- 知识点明确到"模块·知识点"。

---

## 7. 自检清单（模型输出前必过）

- [ ] 每个技能点都有 `skill_point_id`，且与给定清单一致。
- [ ] `anchors` 恰好 5 个键（M1–M5），且单调递进、相邻可区分。
- [ ] 每个锚点都是可观测行为（能写进"我做了什么/说了什么"）。
- [ ] `trigger`：B 型有值，A 型为 `null`。
- [ ] `positive` 是可照说的台词/动作模板。
- [ ] `negative` 是真实常见错误。
- [ ] `evidence_required` 指明引用哪一步的什么记录。
- [ ] `knowledge` 只来自 9 个学习模块。
- [ ] 涉及事实处有 `sources` 或标 `待核实`。
- [ ] 与 10 条硬规则无冲突。

---

## 8. 验收标准（入库前人工/脚本校验）

| 项 | 标准 |
| --- | --- |
| 结构合规 | 通过 `contracts/rubric.py` 的 `Rubric.validate()`（B 型有 trigger、锚点覆盖 M1–M5） |
| 锚点可观测 | 抽查 100% 锚点均可从记录验证 |
| 相邻档可区分 | 抽查 M3/M4 不重复 |
| 知识点合法 | 全部落在 9 个模块内 |
| 事实有据 | 外部事实 100% 有来源或标"待核实" |

> 不达标不入库；入库后由「人工校准集」（PRD 第 25 章）持续校验评分 Agent 的准确率。
