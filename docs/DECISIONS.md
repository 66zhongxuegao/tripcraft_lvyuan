### D-015 · 建立人工校准集，保障评分公信力
- 日期：2026-10-07

### D-021 · 平台只做入境接待，不存在“国内单”
- 日期：2026-10-08
- 决策：所有订单都是入境接待，客源地为港澳台 / 新加坡 / 海外。**中文单同样是入境单**——客人是港澳台或新加坡等中文客源，不是内地客人。

### D-022 · 实战评分接入真实评分 Agent，无证据不给分
- 日期：2026-10-08
- 决策：删除按“订单+技能点”稳定生成的演示分（`score_of()`）。评分只基于**真实证据**（通话转写 / 交付物投递），由评分 Agent 对照 Rubric 判档，结果写入 `order_score` 并回写 `ability.real_v`。
- 细节：每条判定必须带 evidence（PRD 21.2），拿不到证据的技能点**不入库**（返回 dropped）；没有证据的技能点显示“未评估”而非假分。
- 理由：与“幻觉很少、可追溯”的系统目标一致；分数必须能回溯到具体一句话或一份交付物。
- 状态：生效

### D-025 · 导演总线用确定性规则表，不让模型自由发挥
- 日期：2026-10-08
- 决策：学员动作（抢单/首呼结束/发出方案/发出报价/锁定资源/签合同/出团/提交结算）进入事件总线；注入什么事件由**规则表**决定（触发事件 + 平台阶段下限 + 同一规则只投一次），模型只负责用该角色的口吻润色。
- 理由：同一动作必然得到同一刺激，才能反复演示、能解释、能评分；事件注入必须和 B 型考点对应，否则没法算覆盖。
- 状态：生效

### D-026 · 目标技能点清单一旦生成就固定，覆盖率低于 80% 不写画像
- 日期：2026-10-08
- 决策：`build_plan()` 首次生成后写入 `order_target` 并不再重算（导演后续注入的 B 型考点追加进来）；覆盖校验 A 型看交付物、B 型看「触发+学员回应」；覆盖度 < 80% 时本次不写画像（作废而非降权）。
- 理由：清单漂移就无法比较覆盖度；且覆盖不足代表「本次没考到」，写进画像会污染能力值。
- 状态：生效

### D-027 · 低置信度与档位边界判定转人工复核
- 日期：2026-10-08
- 决策：评分 Agent 必须输出 `confidence`；低于 0.7 或分数距 M 档边界 ≤ 3 分，判定记为「待复核」，**不写画像**，由人工采纳/改判/驳回。
- 理由：档位边界（M2/M3）是模型最会漂移的区域（PRD 25.2）；与其盲写不如升级。
- 状态：生效

### D-028 · 双层拦截网：确定性代码硬拦、语义高风险才拦
- 日期：2026-10-08
- 决策：交付物提交前跑两层校验。第一层确定性（分项求和 vs 总价、成本≥售价、保险项、逐日时间轴、四分类）**硬拦**；第二层语义合规只在 severity=高 时拦，余下记为提醒。
- 理由：确定性错误必须拦死；模型判定有漂移，全部当拦截会误伤、当提醒又没意义。拦下的交付物**不投递给客户、不登记证据**。
- 状态：生效

### D-030 · 未过校准的评分 Agent：无基线拦截，未达标降权
- 日期：2026-10-08
- 决策：评分主链读最近一次校准结果。无基线 → 本次不写画像（PRD 25.7 红线）；有基线但未达标 → **降权**：只采信低于掌握门槛（<60）的「暴露薄弱」判定，不允许抬高画像；达标 → 正常写入。
- 理由：25.7 说的是「未经校准集验证不得影响画像」；跑过校准就算验证。未达标时不能盲目相信高分，但“发现薄弱”仍然有价值。
- 状态：生效

### D-031 · 校准集标定策略：一致率达标前提下取最保守阈值
- 日期：2026-10-08
- 决策：计算保留率不低于 60% 的（置信度阈值×档位边界带）组合，取其中**最保守**的一组（阈值最高、边界带最宽）。
- 理由：初版取「保留最多」，在 17 条样本上标定出 0.5/±0，等于关掉了低置信度升级机制；改为在保留率下限内取最保守值，得到 0.9/±3。
- 状态：生效

### D-032 · 校准集先过「结构审计」再谈评测
- 日期：2026-10-08
- 决策：校准集本身要先过 `audit_dataset()`：每个技能点 ≥ 2 条、**M1–M5 全档位都有样本**、至少 2 个客源市场与 2 种语言、含难例（反例命中 / 边界档 / 跨文化红线）。不过审计则不能拿它当验收依据。

### D-053 · 成本 · 损失 · 结算台账：钱的事必须有真账

### D-074 · 访问监控补两项判据：机房/代理标记 + 是否真的操作过
- 日期：2026-10-10
- 问题：只有 IP 与归属地，无法区分「携程真人点开」和「新加坡机房里的扫描器」；实测确实出现过一条新加坡机房 IP 被误当成访客的情况。
- 决策：
  1. 归属地解析时同时取 ip-api 的 `hosting` / `proxy` / `as` 字段，写进记录并在日志与监控窗口里标成「机房」「代理」（中国云主机同样标记，避免上海阿里云上的扫描器冒充上海真人）；
  2. 请求分两类：`renders`（打开页面必然发生：`/`、`/profiles/*`、`/contracts/*`）与 `actions`（非 GET，或 GET 到消息中心/订单/工具台等必须点击才会发生的路径）；
  3. 一个会话写两条记录：首次打开写 `open`，第一次出现真实操作补一条 `interact`，两者用 `session` 字段合并显示，`watch_visits.py` 用 `merge_sessions()` 取最终状态；
  4. 监控窗口新增「行为」列（N页 / N页·操作N次）与统计行（机房代理数、真实操作数）。
- 理由：机房标记看「是不是真人所在网络」，操作计数看「是不是真人行为」，两者合起来才够判断；只靠 IP 归属地会把扫描器误判成客户。
- 状态：生效

### D-075 · 访问监控要能还原「这一趟到底做了什么」
- 日期：2026-10-11
- 问题：一个会话只写 `open` + 首次 `interact` 两条记录，记录里的操作次数是"写入那一刻"的快照。实测有访客在站内抢单、发起语音通话、在聊天里提问、生成学习资源（后端共 230 次请求），日志却只显示「3页·操作1次」，严重低估停留与深度，差点被当成扫描器忽略。
- 决策：
  1. 会话每 45 秒补写一条 `update` 记录（有变化才写），会话闲置回收时再补一条收尾；显示时按 `session` 合并取最新；
  2. 行为摘要加入停留时长（`N页·操作N次·N分`）；
  3. 监控改为纯 ASGI 中间件，同时覆盖 http 与 websocket —— 语音通话走 `/voice/realtime`，原来的 http 中间件看不到，而"发起了语音通话"正是深度体验的关键信号；
  4. `flush()` 改为队列屏障，保证"出队即写完"，避免记录顺序错乱。
- 理由：判断"是不是真人、值不值得当回事"靠的是操作次数、停留时长、是否发起语音这些行为量，只记打开瞬间等于白记。
- 状态：生效

### D-076 · 语音转写必须回写通话记录，否则首呼门槛永远不成立
- 日期：2026-10-11
- 问题：公网访客点了「拨打客户电话」、WebSocket 也建成（`call_session` 落库），但订单最后被判 `deadline_miss:first_call` 超时。查库发现 15 次语音通话里只有 2 次留下转写，且都来自文本通道。
- 根因：事件泵 `_pump()` 把上游（阿里云实时语音）的转写事件映射后直接转发给浏览器，**没有回写数据库、也没有计入 `self.lines`**。而 `_finalize()` 用 `turns = 统计 student 行数` 判断"说过话才算首呼"——语音里学生的话来自上游 ASR，从不进 `lines`，于是 `turns` 恒为 0，语音首呼永远登记不上。
- 决策：`_pump()` 里对上游的**最终转写**（`response.audio_transcript.done` = 客户说的话；`conversation.item.input_audio_transcription.completed/done` = 学生说的话）调用 `_agent()` / `_student()` 落库并计数；中间分片（delta）只转发不落库；同一句话连续重复到达时去重。
- 验证：`tests/test_voice_bridge.py` 5 项；修复后跑 `scripts/smoke_voice_bridge.py`，AI 客户与学生的转写都进了 `call_line`（修复前只有学生那条，因为那是文本通道写的）。
- 待定（未擅自改）：门槛口径是"拨通即算发起首呼"还是"说过话才算完成首呼"。当前保留后者（D-070），若怕评委拨通后不说话被判超时，可改为前者、把沟通质量交给评分 Agent。
- 状态：生效

### D-077 · 拨通即算首呼 + 通话埋点 + 新访客弹窗提醒
- 日期：2026-10-11
- 背景：公网访客点了「拨打客户电话」，订单仍被判超时；事后无法回答「语音模型到底连上没有」——只有浏览器到后端的 WebSocket 有日志，后端到阿里云那一层没有任何痕迹。
- 决策：
  1. **拨通即算发起首呼**：中继收到 `session.updated`（ready）即调用 `record_action(order_id, "first_call", {stage:"dialed"})`。门槛只管"有没有真的发起这一通电话"，聊得怎么样交给评分 Agent（有证据链可查）。`record_action` 幂等，重复调用不会写两条；`_finalize` 里原来的补登记删除。
  2. **通话埋点**：每通电话收尾写一行 `logs/voice_trace.jsonl` —— `ready_ok` / `ready_ms`（语音模型连上没、用了多久）、`audio_in_frames/bytes`（浏览器送上来的麦克风音频）、`audio_out_frames/bytes`（模型返回的音频）、`turns`、`duration_s`、结束原因（`ready_timeout` / `closed`）。超时路径也会写。
  3. **新访客弹窗提醒**：`scripts/visit_alert.py` + `访客提醒.bat`，常驻轮询 `visits.jsonl`，出现新访客时弹 Windows 托盘气泡并响一声；`共享演示.bat` 起隧道时一并启动（最小化窗口）。不需要一直开着监控窗口。
- 验证：`tests/test_voice_bridge.py` 7 项（含拨通登记与埋点字段）；实测冒烟通话 `ready_ok=true, ready_ms=370~472`，`audio_out_frames=24~31`，新订单的 `first_call` 带 `stage="dialed"`；`--test` 能弹出通知。
- 状态：生效
